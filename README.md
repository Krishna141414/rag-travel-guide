# RAG Travel Guide Q&A (Task 8)

Ask a travel question about Indian destinations and get a short answer generated by a **local LLM from retrieved Wikipedia passages**, with numbered source references. If the documents don't cover the question, it says so instead of guessing.

Runs fully locally on CPU: no API keys.

## Problem

General chatbots answer travel questions confidently even when they are wrong or out of date. A RAG (retrieval-augmented generation) app first **retrieves** relevant passages from a fixed document collection and makes the LLM **answer only from them**, so every answer can be checked against its sources, and questions outside the collection can be refused.

## Knowledge base

25 English Wikipedia articles about Indian travel destinations (Munnar, Goa, Jaipur, Varanasi, Leh, Rishikesh, Hampi, Darjeeling, Udaipur, Andaman and Nicobar Islands, Ooty, Agra, Mysore, Kodagu, Khajuraho, Kaziranga, Shimla, Manali, Pondicherry, Amritsar, Jaisalmer, Gangtok, Alappuzha, Mahabaleshwar, Ajanta Caves), about 709k characters. `data/articles.json` is reused from my Task 7 repo ([semantic-search-embeddings](https://github.com/Krishna141414/semantic-search-embeddings)), which downloaded the plain-text extracts through the Wikipedia API.

Article text is from [Wikipedia](https://en.wikipedia.org/), licensed under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/).

## RAG pipeline (`rag.py`)

```
 BUILD ONCE                                                             saved to index/
 articles.json -> clean -> chunk (500 chars, 100 overlap) -> embed (all-MiniLM-L6-v2, 384-d) -> FAISS IndexFlatIP
                                                                                                   (1,774 chunks)
 EVERY QUESTION
 question -> embed -> FAISS top-3 chunks + cosine scores -> best score >= 0.50 ?
                                                              |-- no  -> "I couldn't find this in the travel guide documents."  (LLM not called)
                                                              |-- yes -> prompt: rules + [1] [2] [3] chunks + question
                                                                          -> Qwen2.5-0.5B-Instruct (greedy, max 160 tokens, CPU)
                                                                          -> answer + [n] citations + source cards (title, chunk, score)
```

1. **Ingestion + cleaning**: load the articles; remove pronunciation/IPA groups like `( GOH-ə; Konkani: [ɡɔ̃j] )`, leftover `[...]` marks, empty `()`, section headings with no body, galleries and extra whitespace.
2. **Chunking**: ~500-character windows with 100-character overlap that snap to word boundaries; each chunk keeps `title`, `url` and `chunk_id`.
3. **Embeddings + vector store**: `all-MiniLM-L6-v2` (normalised, so inner product = cosine), exact FAISS `IndexFlatIP`, saved to `index/` on the first run and loaded afterwards.
4. **Retrieval**: top-k = 3 chunks with their similarity scores.
5. **Unanswerable handling**: see below.
6. **Prompt construction**: system rules ("use ONLY the numbered context, cite like [1], say you don't know if it isn't there", plus a one-line example) + numbered context chunks + the question.
7. **Generation**: local `Qwen/Qwen2.5-0.5B-Instruct` (reused from the Hugging Face cache), greedy decoding (temperature 0), `max_new_tokens=160`.
8. **Output**: `answer`, `status` (answered / not_found), `sources` (title, chunk text, score), the exact prompt, and timings.

## How unanswerable questions are handled

Two guards:

- **Retrieval threshold (0.50)**: if even the best chunk scores below 0.50, the app returns *"I couldn't find this in the travel guide documents."* **without calling the LLM** (~10 ms). In the evaluation, out-of-scope questions scored 0.32-0.49 and answerable ones 0.62-0.77.
- **Prompt rule**: if a question passes the threshold but the context still lacks the answer, the LLM is told to reply "I don't know based on the travel guide documents." Example: *"How tall is the Eiffel Tower in Shimla?"* scores 0.55 (it matches Shimla chunks), and the model refuses instead of inventing a height. That reply is also reported as `not_found`.

**Citations**: the 0.5B model often answers correctly but forgets to write `[n]`. For each uncited sentence, the app adds the citation of the source sharing the most words with it, marked with an asterisk (`[2]*`), so automatic citations are never passed off as the model's.

## Results (`evaluate.py` -> `results.md`)

10 questions: 7 answerable (with the expected article) + 3 not in the documents. Models are loaded before timing; CPU only.

| Metric | Result |
|---|---|
| Retrieval hit (expected article in top-3) | 7/7 |
| Answerable questions answered | 7/7 |
| Unanswerable correctly refused ("not found") | 3/3 |
| Answers where the LLM wrote its own citation | 1/7 |
| Avg response time (all 10) | 2.34 s |
| Avg time, answered (LLM called) | 3.34 s |
| Avg time, refused below threshold (no LLM) | 0.01 s |

- **Hero** with a route map connecting the 25 destinations.
- **Requirement cards** (ingestion, chunking/embeddings, retrieval, prompt, LLM answer, unanswerable, evaluation). Clicking one jumps to its demo step; each gets a check mark once the demo has shown it.
- **Live demo**: 5 example buttons. The step bar lights up one step at a time: raw vs cleaned text (removed parts struck out in red) -> chunk count + example chunk + question embedding -> top-3 source cards with score bars against the threshold -> the prompt assembled line by line -> the answer typing out with clickable `[1]` `[2]` citations that highlight their source card. **Open it:**

- **Instant mode (no model needed):** open `web/index.html` directly in a browser. All example outputs are precomputed in `web/demo_data.js` by `build_demo.py` (from real pipeline runs).
- **With the live backend:** run `python app.py` and open http://127.0.0.1:5000. A **Run live** toggle appears; your own question (or an example) is then sent to the real pipeline ("Working... (CPU model, ~10-30 s)").
- `index.html#run=3` auto-starts an example (0-4), which is handy when recording.

## Limitations

- **Small LLM**: Qwen2.5-0.5B gives short, sometimes minimal answers ("December 1961") and writes its own citation only 1 time in 7 (the rest are auto-matched and marked `[n]*`). A larger model (e.g. 1.5B-3B) would answer and cite better but is slower on CPU.
- **Fixed threshold with a thin margin**: "capital of Brazil" reaches 0.47 by matching Goa's Portuguese history, and a paraphrase like "houseboat cruise through backwaters" scores only 0.41 and gets refused.
- **CPU speed**: ~2-5 s per answered question once loaded; the first request after start-up takes longer.
- **Small library**: only 25 destinations from a Wikipedia snapshot, so anything else is "not in documents".
- **No reranking / hybrid search**: a name-only question like "What is the Hawa Mahal?" retrieves Hampi first.

## How to run

```bash
python -m venv .venv
.venv\Scripts\activate                     # Windows
pip install -r requirements.txt            # CPU-only torch via the PyTorch CPU index

python rag.py "Which emperor built the Taj Mahal?"   # one question in the terminal (builds index/ on first run)
python evaluate.py                                   # writes results.md + results.json
python build_demo.py                                 # refreshes web/demo_data.js for the showcase page
python app.py                                        # then open http://127.0.0.1:5000
```

The models (`all-MiniLM-L6-v2`, `Qwen2.5-0.5B-Instruct`) download from Hugging Face on first use, or are reused from the local cache.
